# mincra-srv インシデント調査・対応 引き継ぎ（2026-09-05）

`docs/agents-local-refactoring/tasks.md` の残タスク着手中に、本番ホスト `mincra-srv`
（このセッションの実行環境そのもの）で `agents-index.service` が長期間クラッシュループ
していることが判明し、そこから派生した一連の問題に対応した。以下、発見した問題ごとに
現在の状態と次のアクションをまとめる。

## 1. `gdg` CLI 自己更新のダウングレード連鎖バグ — 修正済み・リリース済み

- **症状**: `sudo gdg agent-host apply --dry-run --diff` が `gdg 0.3.1 → 0.3.0 → 0.1.4`
  と次々に自分自身を書き換え、最終的に `agent-host` サブコマンドが存在しない
  `v0.1.4` に到達して `unknown command "agent-host"` で失敗。途中で本番の
  `/usr/local/bin/gdg`（root 所有）が実際に `v0.1.4` へ書き換えられた。
- **原因**: `cli/internal/command/agent_host.go` の `resolveSpecPath()` は
  `--spec` / `GDG_SPEC` / ライブスペック（`/etc/gdg-agent/agent-host.json`）のいずれも
  無いとき `""` を返し、`LoadSpecWithOverlay("", "")` は **実行中のバイナリに埋め込まれた
  過去時点の `agent-host.json`** を返す（`cli/internal/agenthost/spec.go:93-95`）。
  この埋め込み spec の `pins.gdgCli.version` は「そのリリースを作った時点でのリポジトリの
  次期ピン」であり、必ずしも自分自身のバージョンと一致しない。ライブスペックが存在しない
  ホストでは、`CheckAndReexecSelf` がこの非権威的な埋め込み値を信じて次々に古いバージョンへ
  自己置換し、連鎖が発生する。
- **修正**: `agent_host.go` の `newAgentHostApplyCommand` で、`specPath` が埋め込み
  フォールバック（`""`）由来のときは自己再実行チェック自体をスキップするよう変更。
  `release.go` 側（署名済み Tier 2 リリース／rollback フロー、意図的なダウングレードを
  含む）には一切手を入れていない。
- **副次対応**: 修正のフルテスト実行（pre-commit hook が `go test ./...` を要求）で
  このホスト固有の非再現性のあるテストが2件判明し、あわせて修正:
  - `TestVerifyHostNonExistentUser`（`internal/agenthost`）: 実在しないユーザー名として
    ハードコードされていた `gdgagent-run-0` が、このホストでは実在する本番スロット
    アカウントだった。`user.Lookup` で存在しないことを確認してから使うように変更。
  - `cli/internal/wiki/hooks/gws.test.ts`: 実バイナリ `gws-bin` が存在する環境では
    Google Workspace API に実アクセスしてしまっていた。存在チェックで `t.skip` するよう変更。
- **リリース**: `cli/v0.4.1` として公開済み。`agent-host/agent-host.json` の
  `pins.gdgCli` と `cli/internal/agenthost/backend.go` の `approvedGdgCliDigests` も
  実際のリリース成果物の sha256 で更新済み。
- **コミット**: `572424d`（PR #118, reexec 修正 + テスト2件）、`4c916750a`
  （gdgCli v0.4.1 の pin/digest 更新）。両方 `origin/main` にプッシュ済み。
- **状態**: 完了。ホストの `gdg` は `~/.local/bin/gdg` / `/usr/local/bin/gdg` とも
  `v0.4.1` を実行中。

## 2. `agents-index.service` クラッシュループ — 一部修正、原因追加判明・未修正

- **症状（発見時）**: `agents-index.service` が5秒間隔で再起動を繰り返し、
  再起動カウンタは約25万回（約2週間相当）。`ExecStart` が参照する
  `/opt/gdg-agent/bin/agents-index` が存在せず `status=203/EXEC`。
- **原因**: Stage 13 で `agents-index` の自己完結化（`/opt/agents-index` ソース＋
  `/opt/gdg-agent/bin/agents-index` ラッパー生成）を spec/converger に実装したが、
  このホストでは Stage 10 の control-plane release が一度もブートストラップされておらず
  （`/etc/gdg-agent/agent-host.json` 不在、`agent-host-apply.service`/`.timer` 未導入）、
  実装後に一度も `gdg agent-host apply` が実行されていなかった。
- **経過**:
  1. `sudo gdg agent-host apply --dry-run --diff` で 57 件の差分を確認
     （`/opt/agents-index` 新規作成、`/opt/gdg-agent/bin/agents-index` 新規作成、
     `agent-host-apply.service`/`.timer` 等 Stage 10 の未導入物一式を含む）。
  2. 実行時、`/opt/xangi` の `npm ci` が GitHub Packages 認証エラー（401）で失敗
     — `NPM_READ_TOKEN`（`/home/gdgagent-svc/.config/xangi/secrets.json`）未設定が原因。
     オペレーターが `sudo gdg agent-host secrets set npm-registry` でトークンを設定して解決。
  3. `sudo gdg agent-host apply --diff` 再実行 → 成功終了。
     `/opt/gdg-agent/bin/agents-index` は生成されたが、**サービスは別の原因で
     クラッシュを継続中**（下記）。
- **新たに判明した原因（未修正）**: `agents-index/src/indexer/embed.ts:11` の
  `pipeline("feature-extraction", MODEL, { dtype: "q8" })` が
  `@huggingface/transformers` の `_quantized` サフィックス経由で
  `onnx/model_quantized.onnx` を要求するが、実際の HF リポジトリ
  `intfloat/multilingual-e5-small` にはこのファイルが存在しない
  （実在するのは `onnx/model.onnx` と CPU 特化版 `onnx/model_qint8_avx512_vnni.onnx`
  のみで、後者はライブラリの dtype サフィックス規約に合致しない）。
  この時点でどのホストでも成功したことがない可能性が高い。
  **修正案**: `dtype: "q8"` → `dtype: "fp32"`（`model.onnx` に一致）。
  修正対象は `agents-index/src/indexer/embed.ts`（リポジトリのソース側）で、
  `pnpm sync:agent-host-assets` により `cli/internal/agenthost/assets/agents-index/...`
  へ複製されるため、両方を意識する必要はなく、同期スクリプトに任せればよい。
  `/opt/agents-index/**` は `gdg` バイナリに埋め込まれた asset からレンダリングされる
  ため、この修正を反映するには **`cli/v0.4.2` 相当の新リリースを切って再インストールし、
  再度 `apply` を実行する** サイクルが必要（v0.4.1 と同じ手順）。
- **状態**: 未修正。次のセッションで着手可能。

## 3. `plan.go` の `langfuse-forwarder` パス構築バグ — 未修正・実害あり

- **発見経緯**: 上記 apply 実行後、`git status` で `/home/harineko/gdgjp` 直下に
  想定外の `?? opt/` が出現。中身は `opt/langfuse-forwarder/{package.json,src/**,...}`
  で、root 所有・今回の apply 実行時刻のタイムスタンプ。
- **原因**: `cli/internal/agenthost/plan.go:1005`
  ```go
  destDir := filepath.Join(prefix, "opt", "langfuse-forwarder")
  ```
  `prefix == ""`（ライブモード、`--prefix` 無し）のとき
  `filepath.Join("", "opt", "langfuse-forwarder")` は `"opt/langfuse-forwarder"`
  という **相対パス** を返す（`filepath.Join` は先頭が空文字列だと先頭の `/` を
  保持しない）。他のリソースはすべて `paths.Prefix + "/opt/xxx"` という文字列結合で
  絶対パスを保っており（例: `plan.go:811`）、この 1 箇所だけが例外的に
  `filepath.Join` を使っていたため、`sudo` 実行時のカレントディレクトリ
  （`/home/harineko/gdgjp`）を基準にファイルが書き込まれた。
  同じ脆弱パターン（`filepath.Join(prefix, ...)`）は本リポジトリ内でこの1箇所のみ
  （`grep` で確認済み）。
- **影響**: 本来更新されるべき実体 `/opt/langfuse-forwarder`
  （2025-08-24 頃の古い install.sh 由来、`harineko` 所有）は
  **今回の自己完結化ソースで更新されていない**。`npm-ci:/opt/langfuse-forwarder`
  という exec ステップ自体は絶対パスハードコードのため実際の `/opt/langfuse-forwarder`
  に対して実行され `node_modules` は更新されたが、ソースファイル
  （`src/*.ts`, `package.json` 等）は古いままの可能性が高い。
- **要クリーンアップ**: `/home/harineko/gdgjp/opt/`（root 所有、git 未追跡）を
  `sudo rm -rf` で削除する必要あり。誤って `git add -A` 等で追跡しないよう注意。
- **修正案**: `plan.go:1005` を他箇所と同じ `paths.Prefix + "/opt/langfuse-forwarder"`
  相当の文字列結合に変更し、golden テストで固定。
- **状態**: 未修正。実ホストの `/opt/langfuse-forwarder` が最新化されているかも
  要再確認（`apply` を正しいパスで再実行すれば解消するはず）。

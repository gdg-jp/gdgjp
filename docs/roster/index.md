# roster.gdgs.jp — スタッフシフト表生成アプリ 全体計画

新規ワークスペース `roster/` (`@gdgjp/roster`) を作る計画セット。**人間向けの地図**であり、
`plan-creator` の見出し契約の対象外（`docs/cli-support-url-img-sns/index.md` と同じ扱い）。

**各ステージに着手する前に、必ずこのファイルを最初に読むこと。** ステージファイルはここに書かれた
定数・ドメインモデル・ソルバー仕様を前提にしており、重複記述はしていない。

---

## 1. 何を作るのか

イベント運営のスタッフシフト表を、**登録するだけで自動生成し、その後オーナーが手で直せる**システム。

オーナーは「誰がどの役割で、どのトラックで、何時から何時まで動くのか」をシフト表で把握しなければ
ならない。しかしスタッフの数が多く、シフト表を作ること自体が運営準備のボトルネックになっている。
募集の返信をスプレッドシートに転記し、必要人数を見ながら人力で組み合わせを探し、誰かが辞退すれば
最初から組み直す、という作業が発生している。

さらにスタッフの経験値にはばらつきがあり、**頭数が揃っていればすべて回るとは限らない**。受付や配信
には少なくとも 1 名の経験者が必要な枠があり、初参加者だけを配置すると当日破綻する。満たすべきは
「人数」ではなく「**人数 × 経験の組み合わせ**」である。これは看護師の勤務表作成（ナーススケジューリング
問題）と同じ構造の制約充足問題であり、規模が増えるほど人力では解けない。

一方で最終調整には「この人はこのトラックに慣れている」といったシステムが持たない文脈が必要なため、
完全自動化もできない。したがって**自動生成は最終解ではなく「編集可能なたたき台」として提供する**のが
このプロダクトの基本方針であり、設計上のあらゆる判断がここから導かれる。

### ナーススケジューリング問題との差異

コアは同じ制約充足問題だが、次の違いに合わせて設計する。

| 観点 | ナーススケジューリング | イベントシフト |
|---|---|---|
| 期間 | 数週間〜数ヶ月の周期的な勤務表 | 単日〜数日。使い捨ての一点物 |
| 供給 | 雇用された固定メンバー。稼働は原則所与 | ボランティアの自己申告。当日まで変動する |
| 軸 | 日 × シフト種別（2 次元） | 時間枠 × トラック × 役割（3 次元） |
| 経験 | 資格・年次として明確 | 自己申告。粒度が粗く、役割ごとに異なる |
| 連続稼働の制約 | 労働法規による強い制約 | 体力と離脱防止のための緩い制約 |
| 不満のコスト | 不満があっても雇用関係が続く | 無償のため、次回の募集に応じてもらえない |

供給が当日まで変動する点が、「一度生成して終わり」ではなく「**何度でも再生成・部分編集できる**」ことを
要件にしている。

また「希望の尊重」が目的関数に入るのは、スタッフが**無償のボランティア**だからである。希望しない役割
ばかり、休憩なしの連続稼働では次回の募集に応じてくれない。スタッフ確保が毎回ゼロからやり直しになる
ことが運営の最大コストであるため、「希望役割」「負荷の公平性」「休憩」は親切ではなく**次回の供給を確保
するための投資**として最適化に含める。なお参加者（attendee）の満足度は直接測れないため目的関数には
含めない。

### 運用フロー

1. **設計** — オーナーがイベント / 時間枠 / トラック / 役割 / 必要人数を定義
2. **募集** — 公開 URL を配布し、スタッフ希望者が自分で登録（サインイン必須）
3. **生成** — 募集締切 → 自動生成 → オーナーが手動編集 → 確定
4. **共有** — 閲覧専用 URL でスタッフに公開

### Non-Goal（MVP でやらないこと）

明示的にやらない。ステージの実装中にこれらへ手を伸ばさないこと。

- スタッフ希望者が「見たいセッション」を登録し、それを考慮した割当を行う
- 当日の出退勤打刻、遅刻・欠勤の実績記録
- 交通費・謝礼の計算と精算
- 参加者向けのタイムテーブル公開（セッション情報の管理）
- 会場の動線・混雑のシミュレーション
- 通知・リマインド（メール / Slack / カレンダー連携）
- スタッフ間でのシフト交換申請・承認ワークフロー
- イベントをまたいだスタッフ名簿の蓄積と、実績に基づく経験レベルの自動更新
- シフト表・懇親会リストの CSV / Excel エクスポート（画面閲覧と印刷で代替する）
- RBAC による細粒度の権限管理
- **イベント固有のカスタム Role の作成**（役割はシステムが用意したものから選ぶ）

### P1（MVP 後。この計画セットには含めない）

- スキルミックス条件をハード（必須）/ ソフト（推奨）で切り替える
- 決定済みの割当をロックしたまま再生成する（`assignments.locked` 列とソルバーの `keepLocked`
  オプションは Stage 06/07 で用意するが、**UI は MVP に含めない**）
- トラックと役割の構成をテンプレートから読み込む
- スタッフ登録フォームに、不足している時間帯・役割を表示する
- 公開登録 URL を再発行して古い URL を無効化する
- スタッフが辞退したときの影響範囲と代替候補を提示する
- シフト表と懇親会リストの印刷向けレイアウト

## 3. 用語と定数

**すべてのステージがこの定義を共有する。** 実装時にこの値を変えないこと。

### 経験レベル（`level`）

役割ごとに 3 段階。粒度を粗く保ち、自己申告の精度に依存しすぎないようにする。

| 値 | 表示 | 意味 |
|---|---|---|
| `lead` | リード | その役割を単独で回せる。初参加者を指導できる |
| `exp` | 経験あり | 単独で担当できる |
| `new` | 初参加 | サポートが必要 |

既定は `new`。本人が申告し、オーナーが補正できる。イベントをまたいだ蓄積は行わないため、
毎回の申告が入力源となり、過大・過小申告のリスクはオーナー補正で吸収する。

### 希望度（`pref`）

| 値 | 意味 |
|---|---|
| `1` | 第1希望 |
| `2` | 可 |

（担当できない役割はレコードが存在しない。ソルバー内部では存在しない役割を `3` として扱う）

### 稼働可否（`availability`）

| 値 | 表示 | 意味 |
|---|---|---|
| `o` | ○ | 可能 |
| `d` | △ | 可能なら（`o` で埋まらない場合にだけ使う） |
| `x` | × | 不可 |

### イベントのステータス（`status`）

| 値 | 表示 | 公開登録 URL | 説明 |
|---|---|---|---|
| `draft` | 下書き | 不可 | 設計中。時間枠・役割・需要を編集 |
| `open` | 募集中 | **可** | スタッフ登録を受け付ける |
| `closed` | 締切 | 不可 | シフト生成・編集フェーズ |
| `published` | 公開 | 不可 | シフト確定。閲覧 URL で共有 |
| `ended` | 終了 | 不可 | 読み取り専用 |

**前後どちらにも遷移可能**（再募集できる）。締切以降もオーナーは手動でスタッフを追加できる。
公開閲覧 URL (`/r/:viewToken`) が有効になるのは `published` のときだけ。

### 役割マスタ（シードする 6 件）

| id | 名前 |
|---|---|
| `reception` | 受付 |
| `guide` | 誘導 |
| `mc` | 司会 |
| `stream` | 配信 |
| `photo` | 記録 |
| `setup` | 設営 |

### トラック

割当先の場所・系統。イベントごとに作る。`shared` フラグが立つ「全体」トラックは、受付や誘導のように
全体で 1 セットあればよい役割を置く場所で、トラックごとに需要を重複入力しなくてよくするためにある。
例: 「全体」（shared）、「Track A」、「Track B」、「懇親会」。

## 4. ドメインモデル

**`TimeSlot` を需要・供給・割当・表示すべての共通軸に置くのが設計の中心。** 3 次元の格子
（時間枠 × トラック × 役割）の上で、集計・最適化・グリッド表示がすべて同じ join で済む。
稼働可能時間を自由入力ではなくオーナーが定義した時間枠へのチェックボックスとして受け取るのは、
この一点のためである。

| テーブル | 責務 | 作るステージ |
|---|---|---|
| `user` / `oidc_session` | gdg-lib の RP 認証テーブル | 01 |
| `events` | Chapter に属するイベント | 02 |
| `phases` | 連続する時間枠に付ける名前。需要の一括入力単位 | 02 |
| `time_slots` | 刻み幅で分割した時間枠。`index` を持ち連続性判定に使う | 02 |
| `tracks` | 割当先の系統。`shared` な「全体」を含む | 02 |
| `roles` | 役割マスタ（システム定義・シード） | 02 |
| `event_roles` | そのイベントで使う Role の選択 | 02 |
| `demands` | (time_slot × track × role) の必要人数と経験構成 | 03 |
| `applications` | スタッフ登録 | 04 |
| `application_skills` | (application × role) の経験レベルと希望度 | 04 |
| `availabilities` | (application × time_slot) の稼働可否 | 04 |
| `assignments` | 現在のシフト表 1 枚 | 07 |
| `revisions` | 操作履歴 | 08 |

### 主要な列と制約

**`events`** — `id`, `chapter_id`, `name`, `date`, `start_time`, `end_time`, `step_min`, `tz`,
`status`, `has_party`, `no_solo_newcomer`（既定 true）, `max_consecutive`（既定 4）, `seed`,
`apply_token`, `view_token`, `created_at`, `updated_at`, `deleted_at`。

- `apply_token` / `view_token` は**推測不可能なランダム値**とし、Event ID とは分離する。
  URL から Event ID が推測できてはならない。
- 読み取りは常に `deleted_at IS NULL` で絞る（`scheduler/` の soft-delete 規約に合わせる）。

**`time_slots`** — `id`, `event_id`, `index`（0 始まり、連続）, `start_time`, `end_time`, `phase_id`。
`index` の連続性が、ソルバーの「直前の枠」判定と公開ビューの連続枠まとめの前提になっている。

**`demands`** — `(time_slot_id, track_id, role_id)` に対して `min`（最小必要人数）、`ideal`（理想人数）、
`lead_min`（リードの最小人数）、`new_max`（初参加者の上限）。**ある役割が必要ない時間帯は行を持たない
か `ideal = 0`**。役割の集合そのものが時間帯ごとに変わることを、これで表現する。

**`applications`** — `id`, `event_id`, `user_id`（**NULL 許容**）, `email`, `name`, `party`
(`yes`/`no`/`undecided`), `contact`, `note`, `withdrawn`, `updated_by` (`self`/`owner`),
`updated_at`。

- `UNIQUE(event_id, user_id)` と `UNIQUE(event_id, email)` の**2 本**で二重登録を防ぐ。
- 公開 URL 経由の登録は `user_id` が常に非 NULL。**オーナーの代理登録のみ NULL を許す。**
- オーナーが上書きした値は本人の申告値と別に保持しない。**最後に書いた側が勝つ。**
  誰がいつ更新したか（`updated_by` / `updated_at`）だけを残す。

**`assignments`** — 主キーは `(application_id, time_slot_id)`。**この形にすることで「同一スタッフを
同一時間枠に 2 箇所へ割り当てない」という最重要のハード制約を構造的に禁止する。** 列は
`track_id`, `role_id`, `locked`。

## 5. ソルバー仕様

`app/features/solver/` に置く純 TS。**UI にも D1 にも依存しない。** 入力はプレーンなオブジェクト、
出力は割当と評価レポート。Stage 06 で単体実装し、Stage 07 が Worker の action から呼ぶ。

### 5.1 絶対に破らない条件（ハード制約）

自動生成ではこれを破る割当を作らない。

1. 同一スタッフを同一時間枠に 2 箇所へ割り当てない
2. 稼働不可（`x`）の時間枠に割り当てない
3. 担当できない役割に割り当てない
4. 需要のない枠に割り当てない
5. スキルミックス条件（`lead_min` / `new_max` / 初参加者の単独配置禁止）を満たす
6. 辞退したスタッフを割り当てない

**手動編集ではこれらを警告のうえ許可する。** 当日の例外運用があるため禁止はしない。
これは意図的な非対称であり、実装時に「一貫性のため」と称して手動編集側を禁止に倒さないこと。

### 5.2 生成フロー（7 段）

1. **需要セルを希少度順に並べる。** 希少度 = （担当可能かつ稼働可能な人数） − `min` + リード余裕度。
   リード余裕度は `lead_min > 0` なら `(リード可能人数 − lead_min) × 0.5`、`lead_min = 0` なら `5`
   （リード条件のない枠を後回しにする）。同値なら時間枠の `index` 昇順。
2. **リードの最小人数を先に確保する。** `lead` レベルの候補だけを対象に `lead_min` まで埋める。
3. **最小必要人数まで充足する**（第1パス、目標 = `min`）。
4. **理想人数へ近づける**（第2パス、目標 = `ideal`）。
5. **局所探索で負荷を均す。**
6. **初参加者だけになった枠を、同時間帯の経験者と入れ替える**（OJT ペアリング）。
7. **評価して不足の内訳を報告する。**

第 2〜4 段で初参加者を追加するときは、`new_max` を超えないこと、および
`no_solo_newcomer` が有効なら「最後の 1 席を埋める時点で経験者が同席していない」場合に
初参加者を選ばないこと、の 2 条件を満たす候補だけを対象にする。

### 5.3 候補コスト（低いほど先に配置）

加点方式ではなく、**「不満のコスト」を最小化する減点方式**で書く。

| 項目 | コスト | 理由 |
|---|---|---|
| 稼働 `o` | `0` | |
| 稼働 `d`（△） | `+4.5` | `o` で埋まらない場合にだけ使う |
| 稼働 `x`（×） | `+Infinity` | ハード制約 |
| 第1希望の役割 (`pref === 1`) | `−6` | 希望しない役割ばかりでは次回の募集に応じてもらえない |
| 担当可 (`pref === 2`) | `0` | |
| それ以外 (`pref` なし) | `+3` | |
| 総稼働枠数 | `+1.6 × 現在の割当数` | 負荷の公平性 |
| 直前の枠と同じトラック・役割 | `−3.5` | 引き継ぎ回数を減らす |
| 直前の枠と別トラック | `+1.2` | トラック間の移動時間を減らす |
| 連続稼働が `max_consecutive` に到達 | `+12` | 休憩枠を確保する |
| 連続稼働が `max_consecutive − 1` | `+4` | |
| その役割で `lead` である | `+0.8` | 経験者を一箇所に集めず、トラック間に散らす |
| タイブレーク | `+ rng() × 0.4` | 同点時。シード固定なので再現する |

### 5.4 再現性（必須要件）

乱数は `mulberry32(seed)` を使う。**同じ入力と同じシードなら必ず同じ結果を返す。**
`seed` は `events.seed` に保存し、再生成時も同じ値を使う。オーナーがシードを変えて再生成すると
別の解が出るので、履歴上で指標を比較できる。

```ts
function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a |= 0;
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

### 5.5 局所探索

負荷が重いスタッフの割当を、まだ余裕のある同等スタッフへ移す。**厳密解は狙わず、目に見える偏りだけを
取り除く。**

- 最大 40 パス。`max(load) − min(load) <= 2` になったら打ち切る
- 最も重いスタッフを乱数で 1 人選び、その `locked` でない割当を 1 つ、`load <= min` かつ
  稼働が `o` のスタッフへ移す
- **移した結果 `lead_min` を割る、または `new_max` を超える場合は移さない**
- 1 パスで 1 件も移せなければ打ち切る

### 5.6 OJT スワップ

初参加者だけで構成された枠を、同じ時間帯の別の枠にいる経験者と入れ替える。

- **入れ替え先に経験者が残ることを保証する。** 崩せない場合は入れ替えない
  （無理に動かすより、違反として報告するほうが役に立つ）
- 入れ替え先の `lead_min` / `new_max` も守る
- 両者がそれぞれ相手の役割を担当できることを確認する

### 5.7 評価レポート

`evaluate(state, assignments)` は以下を返す。手動編集後も同じ関数で再評価する。

**不足（shortages）** — `headcount`（`min` 未満）と `lead`（`lead_min` 未満）を**区別して**返す。
**違反（violations）** — `newcomerOver`（`new_max` 超過）、`soloNewcomer`（初参加者だけの枠）、
`over`（`ideal` 超過。手動編集の結果なので不足とは分けて扱う）。

**指標（metrics）** — `minShortage`（頭数の不足合計）、`leadShortage`（経験者の不足合計）、
`idealRate`（理想充足率）、`firstChoiceRate`（第1希望の役割に割り当てられた割合）、
`loadStdev` / `loadMax` / `loadMin`（負荷のばらつき）、`softUsed`（△ を使った枠数）、
`overwork`（連続稼働が上限を超えたスタッフ）、`violationCount`。

### 5.8 充足不可能性の検出

**これが自動生成のもう一つの価値である。** 条件を満たす解が存在しない場合、無理に解を出すのではなく
「どの時間枠のどのトラック・役割で何が足りないのか」を報告する。

**頭数の不足と経験者の不足を区別する**ことで、募集の告知内容（「配信経験者を募集中」）に直接反映できる。
UI では「解なし」と表示せず、3 列（頭数の不足 / 経験者の不足 / 経験構成の違反）に分けて出す。

### シフト表の見せ方（Stage 07）

**縦軸に時間、横軸にスタッフ**を置く。1 列が 1 人のその日の動きになり、横に読めば「今この時間、誰が
どこにいるか」が分かる。

- **セルの中身** — 役割名。担当がない時間は空欄で、**休憩として読める**
- **セルの色** — トラックを区別する。縦に色が続けば同じ場所に留まっており、色が変わればトラック間の
  移動が発生していると分かる
- **色だけに頼らず、セル内にトラック名も併記する**（アクセシビリティ）
- **経験レベルは列ヘッダに示し、セル内には出さない**（情報量を抑えるため）

補助ビューとして、**縦軸に時間、横軸に (トラック × 役割)** を置いた需要ビューを用意し、充足状況を
色で示す。縦軸を時間に揃えることでシフト表と並べて読める。

### 権限モデル（MVP はフラット）

| 主体 | できること |

| スタッフ希望者（サインイン済み） | 自分の登録の作成・編集・辞退 |
| 閲覧 URL を知っている人 | 公開されたシフト表の閲覧のみ |

権限判定は `app/features/auth/permissions.ts` に集約する。将来 RBAC を入れる際の変更点をここに

## 8. 全ステージ共通の制約

**理由つきで書いてある。理由のない禁止は、都合が悪くなると回避される。**

- **`roster/schema.sql` は生成物。** 手で編集せず `pnpm --filter @gdgjp/roster migrate:local` で
  更新する。マイグレーションを直すこと。
- **`worker-configuration.d.ts` は生成物。** `wrangler.toml` のバインディングを変えたら
  `pnpm --filter @gdgjp/roster cf-typegen` を実行する。手編集しない。
- **`tests/architecture/` の allowlist を増やさない。** allowlist は縮小専用。追加は「分割できな
  かった」を遠回しに言っているだけで、規約を骨抜きにする。
- **`app/lib/` に新規ファイルを足さない。** ドメインを持つコードは `app/features/<domain>/` へ。
  `layering.test.ts` がホワイトリストで固定している。
- **ソルバーは D1 にも React にも依存させない。** 入出力はプレーンなオブジェクトに保つ。
  これが単体テストと再現性検証を成立させている唯一の条件。
- **`assignments` の主キー `(application_id, time_slot_id)` を変えない。** これがハード制約
  「同一枠 2 箇所禁止」の実装本体である。
- **手動編集のハード制約チェックを「禁止」に倒さない。** 警告して続行させる。当日の例外運用がある。
- **経験レベルを公開ビュー (`/r/:viewToken`) に出さない。** ADR-005 の決定であり、
  Stage 09 の architecture テストで固定する。
- **lockfile を勝手に変えない。** 依存追加が必要なら計画に明記されているものだけにする。

# Stage 1 — raw 層の新設（`sources`）

> Generated from Claude Code plan: `/Users/hari/proj/gdgjp/docs/plans/01-sources-raw-layer.md`
> 全体方針: `docs/plans/00-llm-wiki-overview.md`

## Goal

一次情報（raw）を Wiki ページから切り離し、運営メンバーが URL を投げ込める受け皿を `wiki/` に作る。

現行の Google Docs import は Doc のタブを 1:1 で Wiki ページ化するため、`page-1786197821498` のような機械スラッグが 107 件サイドバーに並び、UX を壊している。
raw を別テーブル・別 UI に隔離し、Wiki ページは LLM が書いた合成物だけにする。

これは LLM Wiki パターン（`llm-wiki.md`）の三層構造のうち Raw 層にあたる。後続の Stage 2〜5 がこの上に乗る。

## Acceptance criteria

### 1. データモデル

`wiki/app/db/schema.ts` と `wiki/migrations/00XX_add_sources.sql` に 3 テーブルを追加する。
マイグレーションは**手書き SQL**（Drizzle 生成を使わない）。`schema.sql` は `migrate:local` が再生成するので手で触らない。

| 列 | 型 | 備考 |

| `kind` | text | `google-doc` \| `google-chat-space` \| `website` \| `upload` \| `text` |
| `external_id` | text nullable | Google Doc ID など |
| `url` | text | 正規化済み URL |
| `title` | text | 取得時に確定 |

| `added_by` | text FK → `user.id` | |
| `status` | text default `pending` | `pending` \| `fetching` \| `ready` \| `error` \| `archived` |

### 2. R2 レイアウト

```
raw/<sourceId>/<sourceDocumentId>/<contentHash>.md
raw/<sourceId>/assets/<assetId>-<fileName>
```

再取得はハッシュの異なる**新しいオブジェクトを書き**、`source_documents.r2_key` を差し替える。
**旧オブジェクトは削除しない。** これで raw の不変性が担保され、「前回 Ingest 時点から何が変わったか」が差分で取れる。

既存と同じハッシュなら R2 書き込みも `captured_at` 更新もスキップする。

### 3. API

`wiki/app/routes.ts` に登録する。すべて `requireUser` で保護し、`chapter_id` によるスコープを効かせる。

- `POST /api/sources` — URL を受け取り `kind` を判別して `pending` で登録、`SOURCE_FETCH_QUEUE` に投入
- `GET /api/sources` — 一覧（ステータス、最終取得日時、document 数）
- `POST /api/sources/:id/refresh` — 再取得をキューに積む
- `POST /api/sources/:id/archive` — アーカイブ（R2 は消さない）

`kind` 判別は既存の `isGoogleDriveUrl` / `isGoogleFormUrl` を再利用する。

### 4. UI

- `/sources` ルートを新設し、`routes/_app.tsx` レイアウト配下に置く
- **サイドバーのページツリーには出さない。** `_app.tsx` のサイドバーフッターで「設定」の直上に「ソース」エントリを追加する
- 画面要素: URL 入力欄、ソース一覧テーブル、各行のステータスバッジ・再取得・アーカイブ操作、展開すると `source_documents` の一覧
- i18n 文字列は `wiki/app/locales/{ja,en}/common.json` に追加する（既定 `ja`）

### 5. 取得ワーカー

新規ディレクトリ `wiki/workers/features/sources/` を作る。

- `fetch-source.ts` — ディスパッチャ。`kind` で fetcher を選び、結果を `source_documents` + R2 に確定する
- `google-doc.ts` — `tools/google-drive.ts` と `tools/google-docs/workspace.ts` を再利用。タブ 1 つ = `source_document` 1 件、`path` はタブ階層をスラッシュで繋いだもの。**出力先を pages ではなく `source_documents` + R2 に変えるだけ**
- `website.ts` — `tools/web-fetch.ts` と `BROWSER` バインディングを再利用
- `persist.ts` — ハッシュ計算、R2 書き込み、`source_documents` upsert を集約

`workers/features/ingestion/` の内部実装を UI ルートから直接 import しないという既存の層規約
（`wiki/workers/features/ingestion/README.md`）を踏襲する。

### 6. Queue と cron

`wiki/wrangler.toml` に既存の `GOOGLE_DOCUMENT_IMPORT_QUEUE` と同じ形で追加する。

```toml
[[queues.producers]]
binding = "SOURCE_FETCH_QUEUE"
queue = "gdgjp-wiki-source-fetch"

[[queues.consumers]]
queue = "gdgjp-wiki-source-fetch"
max_batch_size = 1
max_batch_timeout = 30
```

`wiki/workers/app.ts` の `queue` ハンドラに判別分岐を追加する。
判別不能なメッセージは既存規約どおり `ack()` で落とす（`wiki/CLAUDE.md`）。
型ガードは `queue-processors.server.ts` の `isGoogleDocumentImportQueueBody` に倣う。

`refresh_policy` が `manual` 以外のソースを定期再取得する cron を足す。
`[triggers].crons` に 2 本目を追加し、`scheduled` ハンドラの `event.cron` 判別子を**同時に**更新する。
既存は `0 15 * * *` 1 本のみで cron を判別していないため、判別分岐の導入も含む。

### 7. 検索からの除外

raw は `pages` に入らないので Vectorize と全文検索からは自然に外れる。
リグレッションを防ぐため、`/search` と `wiki/app/features/ai-search/` のテストに
「`sources` 由来のコンテンツが結果に出ない」ケースを追加する。

## How to verify

```bash
pnpm --filter @gdgjp/wiki migrate:local
pnpm --filter @gdgjp/wiki cf-typegen
pnpm --filter @gdgjp/wiki test
pnpm ci:quick
```

`wrangler.toml` のバインディングを変えたら **必ず `cf-typegen` を走らせる**（`worker-configuration.d.ts` は生成物なので手で編集しない）。

ユニットテストで固定すること:

- 同じ内容を再取得したとき R2 に書き込まれず `content_hash` が変わらない
- `(source_id, path)` の UNIQUE 制約が効いている
- `SOURCE_FETCH_QUEUE` 以外のメッセージ形が `queue` ハンドラで `ack()` される
- 判別不能な URL が `POST /api/sources` で 4xx になる

手動 E2E:

1. `pnpm --filter @gdgjp/wiki dev`（:5177）
2. Google Drive 連携済みのユーザーでサインインし `/sources` を開く
3. Google Docs の URL を登録 → ステータスが `pending` → `fetching` → `ready` に遷移する
4. `.wrangler/state` の D1 を引いて `source_documents` にタブ数ぶんの行と `content_hash` があることを確認する
5. 同じ URL を再取得しても `content_hash` が変わらず `captured_at` だけ更新されることを確認する
6. **サイドバーに新しいページが現れないことを確認する**

## Constraints

- `wiki/` 以外のワークスペースを変更しない。`cli/` は Stage 3 の担当なので触らない
- 既存の `google_document_imports` / `google_document_import_nodes` と Google Docs import 経路は**このステージでは削除も変更もしない**。移送は Stage 4 で行う
- `wiki/schema.sql` と `wiki/worker-configuration.d.ts` は生成物。手で編集しない
- マイグレーションは手書き SQL。Drizzle の generate を使わない
- Biome 準拠（2 スペース、ダブルクォート、セミコロン、末尾カンマ、100 桁）
- `verbatimModuleSyntax` のため型のみの import は `import type` を使う
- `.server.ts` はサーバー専用。クライアントコードから import しない
- バインディングは `context.cloudflare.env` 経由で参照する
- 依存パッケージを追加しない（`pnpm-lock.yaml` を変更しない）
- 秘密情報をコミットしない

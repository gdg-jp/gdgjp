# デザインシステムで prototype と mockup を作る

## この skill がすること

依頼を、`@gdgjp/design-system` で組んだ画面の HTML に変えます。
成果物は 1 つのディレクトリにまとめます。

| ファイル | 中身 |
| --- | --- |
| `spec.md` | PRD・機能構成・コンポーネント選定。HTML の「仕様」タブに表示する |
| `prototype.tsx` | 画面・状態・主要フローの定義（必要なら同じディレクトリの複数ファイルに分ける） |
| `index.html` | 外部ファイルに依存しない 1 枚の HTML。「画面一覧」（mockup）、「操作」（prototype）、「仕様」の 3 タブを持つ |
| `shots/` | 検証用のスクリーンショット。成果物ではない |
| `.build/` | ビルドの作業場所。`.build/check/check.html` は手で確かめるときに開く |

`index.html` は、ブラウザーで開くだけで動きます。
画面一覧タブには全画面・全状態が縮小表示で並び、クリックすると実寸で見られます。
操作タブでは、デスクトップ幅とモバイル幅を切り替えながら実際に操作でき、主要フローの手順（シナリオ）も確かめられます。
どちらのタブもライト／ダークを切り替えられます。

## 前提

- `packages/design-system/` の submodule が初期化され、`pnpm install` 済みであること。
  足りなければスクリプトが具体的なコマンドを表示して止まる。
- スクリプトはリポジトリのルートから `node .claude/skills/design-prototype/scripts/<name>.mjs` で実行する。
  以下、`$SKILL` はこの skill のディレクトリ（`.claude/skills/design-prototype`）を指す。

## 進め方

### 1. 作業ディレクトリを決める

ユーザーが場所を指定していなければ、セッションの scratchpad ディレクトリの下に `prototypes/<slug>/` を作る。
`<slug>` は英小文字のケバブケースにする（例: `event-checkin`）。

リポジトリの中には置かない。
prototype は検討用の使い捨てで、本番コードや `docs/` と混ざると後で邪魔になるため。

### 2. PRD を下書きして、確認する

[references/spec-template.md](references/spec-template.md) を読み、`spec.md` の PRD 章を依頼内容から下書きする。
PRD は次の 5 節で書く。

| 節 | 書くこと |
| --- | --- |
| Overview | 1〜2 文の要約と、Who・What・When・Where・Why・How の 5W1H 表 |
| Goal / Non-goal | 達成したい結果（観察か計測ができる形）と、扱わないこと |
| Proposed solutions | Goal ごとの解決策。仕組みと振る舞いで書き、画面の配置は機能構成に回す |
| User stories | 誰が、いつどこで、何を、なぜしたいか。対応する Goal と優先度を付ける |
| Open questions / Risks | 決まっていないことと今の仮定、決めても残る不確かさ |

書くときは次の 3 つを守る。
それぞれの具体的な基準は spec-template.md の 2 章にある。

- **Less is more:** 画面を決めるのに要る行だけを残す。「この行が消えたら画面の何が変わるか」に答えられない行、一般論、形容詞は消す。
- **MECE:** Goal 同士が重ならず、合わせると Why を言い尽くす。すべての story と solution がどれかの Goal に対応し、すべての Goal に story がある。Goal と Non-goal、Question と Risk を混ぜない。
- **5W1H:** 5W1H 表に空欄を残さない。分からない行は仮定で埋め、Open questions に載せる。画面の形を決めるのは主に Who・When・Where なので、役割名だけでなく状況まで書く。

下書きを確認に出す前に、spec-template.md の 4 章のセルフチェックを通す。

既存アプリ（`apps/<app>/`）に関わる依頼なら、下書きの前に次を読む。
画面の形を決める前提（範囲外の機能、公開範囲、権限、利用者の端末）が書かれていることが多く、読まずに進めると PRD を誤る。

- 関係するアプリと docs を `ls apps/` と `ls docs/` で探す。ルートの CLAUDE.md のアプリ一覧は網羅的ではなく、docs はアプリ名を含む複数のディレクトリ（例: `docs/wiki-*`）に分かれていることがある。
- `apps/<app>/CLAUDE.md` と `ARCHITECTURE.md`、docs の計画・ADR。長いので、まず Non-Goal、権限、公開範囲、個人情報の扱いの節を探して読む。
- 改善の対象になる画面のルート（`apps/<app>/app/routes/`）。
- 画面に出すデータの形は、上流の API、マイグレーション、モデル（例: 参加者なら `apps/connpass/`）で確かめる。

依頼にもリポジトリにも書かれていないことは、もっともらしい仮定で埋め、Open questions に「仮定（未確認）」として載せる。
ここで手を止めて質問攻めにはしない。

下書きができたら、Open questions のうち画面の形を大きく変えるものだけを、**AskUserQuestion で 2〜4 問まとめて**聞く。
質問ごとに推奨案を 1 つ目の選択肢に置き、ほかの案と比べて選べるようにする。

聞く価値が高い論点は次のとおり。

- 主な利用者と使う場面・端末（5W1H の Who・When・Where。PC 中心か、スマートフォン中心か）
- この prototype で扱う範囲（Goal と Non-goal の境目、どのストーリーまで操作できるようにするか）
- 主要フローの分岐（承認の有無、下書き保存の有無など）
- 画面に出すデータの粒度
- 依頼の言葉が複数の意味に取れ、意味によって画面が変わるもの（例: 「種類」がページの分類か、検索対象の種類か）

聞く必要がないものもある。
リポジトリの docs で分かること、色や文言の細部、デザインシステムが決めていること（ボタンの形、間隔など）は聞かない。

回答を PRD に反映し、聞いた Question は Open questions から消す（決まったことは該当する節に書く）。
そのあと、機能構成以降は確認を挟まずに最後まで進める。
途中の成果物は、最後に HTML と一緒に見せる。

質問しない場合もある。
ユーザーが最初から「おまかせ」「確認なしで」と言っている場合や、AskUserQuestion が使えない場合は、推奨案を選んだものとして進める。
そのときは、選んだ案を Open questions の「今の扱い」に「仮定（未確認）」として残す。
レビューする人が、後から論点を拾えるようにするため。

### 3. 機能構成を決める

`spec.md` の「機能構成」章を書く。

- **画面一覧:** すべてのユーザーストーリーが、どれかの画面に対応するようにする。
- **画面遷移:** 主要フローを矢印の図で書く。ここに書いたフローは、手順 5 で `flows` になる。
- **画面ごとの状態:** 利用者が実際に出会う状態（通常、0 件、入力エラー、確認ダイアログ、モバイルなど）を挙げ、それぞれに frame id を付ける。この表の行が、そのまま mockup のフレームになる。
- **データ:** 画面に出す項目だけを書く。

依頼に「比較したい」「いくつか案を」とあれば、2〜3 案を作る。
案の違いはレイアウトと情報の置き場所に絞り、画面一覧と状態の表は案ごとに書く。

### 4. コンポーネントを選ぶ

まず、使える部品と正確な export 名を確かめる。

```sh
node $SKILL/scripts/components.mjs
```

次に `packages/design-system/DESIGN.md` の「## Components」と「## Do's and Don'ts」を読む。
DESIGN.md は、部品の使い分け（`RadioGroup` と `Select` の違い、`Tooltip` に必須情報を入れない、など）を決めている。
`components.mjs` で「Other」に入る部品は、DESIGN.md の分類に名前が出てこないだけで、使ってよい。

使うと決めた部品のうち、使い方に自信がないものは、`components.mjs` が示す story ファイルを読んで props と組み合わせ方を確かめる。
推測で prop を書くと型チェックで止まり、かえって時間がかかる。

ここまで決めたら、`spec.md` の「コンポーネント選定」章に、画面・領域ごとの部品と選んだ理由を書く。
デザインシステムで足りなかった部分や、見た目を上書きした部分は「デザインシステムにないもの」に残す。
これはデザインシステムを改善するときの材料になる。

### 5. 組み立てる

[references/authoring.md](references/authoring.md) を読んでから `prototype.tsx` を書く。
要点は次の 4 つ。

- 画面コンポーネントは props だけで描画が決まる純粋な関数にする。フレームと App の両方から同じ部品を使うため。
- `frames` は「画面ごとの状態」表と 1 対 1 にする。
- `App` は `useState` で画面遷移とデータの変化を持ち、主要フローを最後まで操作できるようにする。
- 主要フローを `flows` に手順として書く。check.mjs がその手順どおりに App を操作し、動くことを確かめる。

複数の利用者が登場するフロー（申請 → 承認など）や、複数案の比較では、`controls`（prototype 専用の切り替え）を使う。
書き方は authoring.md の 5 章にある。

### 6. 検証する

```sh
node $SKILL/scripts/check.mjs <dir>
```

`check.mjs` は次のことを順に行い、結果を 1 行ずつ出力する。

1. 型チェックをして、開発ビルドを作る。
2. 画面一覧と全フレームを、フレームと同じ大きさで描画して撮る。
3. `flows` の各手順を App 上で実行し、手順ごとに撮る。
4. コンソールのエラーと警告、横へのはみ出し、見えている primary ボタンの数、フレームの下に続く内容の量を報告する。

ダークテーマも確かめるときは `--dark` を付ける。
通常は 1 分以内に終わる。
出力は 1 行ずつ出るので、`tail` や `grep` に通さずにそのまま読む。
読み方と、長引いたときの見分け方は authoring.md の 8 章にある。

`error` がなくなり、`warning` も直すか理由を説明できる状態になったら、スクリーンショット（`<dir>/shots/`）を Read で実際に見る。
少なくとも、各画面の代表的なフレーム、モバイルのフレーム、各フローの最後の手順は確認する。
見る観点は次のとおり。

- spec.md の状態がそのとおりに表現されているか（0 件なのに一覧が出ていないか、など）
- はみ出し、重なり、文字の詰まり、見出しの不自然な折り返しがないか
- 色や階層が意図どおりか（警告に出ない種類の問題は、目で見ないと分からない）
- 文言が自然な日本語か
- フレームにしかない状態（App では起こせない状態）が、意図どおりか。意図どおりなら spec.md の状態の表に書いておく

直したら `check.mjs` をもう一度実行する。

### 7. ビルドして渡す

```sh
node $SKILL/scripts/build.mjs <dir>            # 軽量版（数百 KB、フォントはシステムフォント）
node $SKILL/scripts/build.mjs <dir> --fonts    # Google Sans と Noto Sans JP を埋め込む（約 8 MB）
```

既定は軽量版でよい。
他の人に共有する、見た目を厳密に確かめる、とユーザーが言ったときだけ `--fonts` を使う。
フォントを埋め込むとフレームごとにフォントを読み込むため、画面一覧タブが重くなる。

最後に、ユーザーへ次の 3 つを短く伝える。

- `index.html` の絶対パス。`open <path>` で開けることも添える。
- 作った画面と状態の数、操作タブで辿れるフロー。
- Open questions / Risks に残した仮定と、「デザインシステムにないもの」に書いた項目。

共有したいと言われたら、Artifact ツールで `index.html` を publish すれば非公開のリンクになる。
HTML はこの skill のビルドが生成したものなので、手で書き換えない。

修正の依頼を受けたら、同じディレクトリの `spec.md` と `prototype.tsx` を直し、手順 6 と 7 をやり直す。
PRD が変わる修正なら、先に `spec.md` を直してから画面に反映する。

## 判断に迷ったとき

- **デザインシステムに合う部品がない:** まず既存部品の組み合わせ（`Card` + `Stack` + `Inline` + Tailwind のトークンユーティリティ）で作る。それでも無理なら、prototype の中に小さな部品を自作し、spec.md の「デザインシステムにないもの」に理由を書く。デザインシステム自体は変更しない。
- **依頼が大きすぎる:** 主要ストーリー（Must）の画面だけを作り、残りは PRD の Non-goal に送る。目安は 3〜8 画面、フレーム 20 枚以内。複数案なら 1 案あたり 4〜6 フレーム。
- **既存アプリの画面を改善したい:** 今の画面の情報構造と困りごとを PRD の Overview（Why）に書いてから進める。prototype はデザインシステムで組み直したものにし、既存のコードは import しない。アプリ独自の `DESIGN.md` があれば用語と情報の優先度を知るために読むが、見た目はデザインシステムに従う。
- **既存アプリに機能を足したい:** 手順 2 の docs を必ず読み、その機能がアプリの Non-Goal に入っていないか、権限と公開範囲の決まりは何かを確かめ、PRD の Proposed solutions の「守る制約」に書く。アプリの Non-Goal に入っている機能なら、そのことを Overview の Why と Open questions / Risks に明記したうえで作る。

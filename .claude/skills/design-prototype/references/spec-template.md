# spec.md のテンプレート

`spec.md` は、PRD・機能構成・コンポーネント選定を 1 つにまとめたファイルです。
ビルドすると HTML の「仕様」タブに表示され、mockup をレビューする人は、何を満たすための画面なのかをこのタブで確かめます。
そのため、読み手は依頼者とは限らないと考えて書きます。

各見出しの役割は次のとおりです。

- **PRD:** 「何を、なぜ」。課題・利用者・ユーザーストーリー・範囲・成功基準を書く。
- **機能構成:** 「どんな画面と流れで」。PRD のユーザーストーリーをすべて画面に割り当てる。
- **コンポーネント選定:** 「どの部品で」。機能構成の各画面を `@gdgjp/design-system` の部品に落とす。

前の章が決まらないと後の章は書けません。
後の章で矛盾が見つかったら、前の章に戻って直します。

````markdown
# <プロダクト名・機能名>

> <1〜2 文の要約。誰の、どんな課題を、どう解くか>

## PRD

### 背景と課題

<今どうなっていて、何が困るのか。具体的な場面を 1 つ以上>

### 利用者

| 利用者 | 立場・状況 | この機能でしたいこと |
| --- | --- | --- |
| <例: チャプターのオーガナイザー> | <例: 月 1 回イベントを開く。PC で作業> | <…> |

### 目的と成功基準

- 目的: <…>
- 成功基準: <観察・計測できる形で。例: 参加登録の確認が 3 クリック以内で終わる>

### ユーザーストーリー

| ID | ストーリー | 優先度 |
| --- | --- | --- |
| US-1 | <利用者> として <したいこと> したい。<理由> のため。 | Must |
| US-2 | … | Should |

### 範囲

- 含む: <できること。画面名ではなく「何ができるか」で書く。例: 交代を申請できる、オーナーが承認・却下できる>
- 含まない: <この prototype では扱わないこと。後で検討することも含めて書く>

### 前提と未決事項

- 前提: <確認せずに置いた仮定。仮定には「仮定」、確認できなかったものには「仮定（未確認）」と書く>
- 未決: <まだ決まっていないこと。確認できずに仮定で進めた論点も、ここに残す>

## 機能構成

### 画面一覧

| 画面 | 目的 | 主な操作 | 対応ストーリー |
| --- | --- | --- | --- |
| <イベント一覧> | <…> | <検索、作成、詳細へ> | US-1, US-2 |

### 画面遷移

```text
イベント一覧 ──[作成]──▶ 作成ダイアログ ──[保存]──▶ イベント一覧（トースト）
     │
     └──[行を選択]──▶ イベント詳細 ──[削除]──▶ 確認ダイアログ
```

### 画面ごとの状態

mockup に並べるフレームは、この表の行と 1 対 1 で対応します。
起こりうる状態だけを挙げてください（すべての画面に「エラー」が要るわけではありません）。

| 画面 | 状態 | どんなときに起きるか | frame id |
| --- | --- | --- | --- |
| イベント一覧 | 通常 | 予定が数件ある | `events` |
| イベント一覧 | 0 件 | 初めて使う | `events-empty` |
| イベント一覧 | 通常（モバイル） | スマートフォンで確認 | `events-mobile` |
| 作成ダイアログ | 入力エラー | 必須項目が空のまま保存 | `create-error` |

### データ

画面に出す項目だけを書きます（DB 設計ではありません）。

| もの | 項目 |
| --- | --- |
| イベント | 名前、開催日、開催形式（会場／オンライン／ハイブリッド）、公開状態、参加者数 |

## コンポーネント選定

| 画面・領域 | コンポーネント | 選んだ理由・使い方 |
| --- | --- | --- |
| 全体の枠 | `AppShell` | サイドバー付きの管理画面。モバイルでは Sheet に畳まれる |
| 一覧 | `Table` + `Badge` | 比較が要る構造化データ。公開状態は `Badge` の tone で表す |
| 0 件 | `EmptyState` | 作成ボタンを `action` に置く |
| 作成 | `Dialog` + `FormField` + `Input` | 項目が少なく、一覧の文脈を保ったまま作成できる |
| 結果通知 | `toast` | 成功だけに使う。エラーは `FormField` の `error` に出す |

### デザインシステムにないもの

<既存コンポーネントの組み合わせで代用したもの、代用できず自作したもの、見た目を上書きしたものと、その理由。
なければ「なし」と書く。デザインシステムへの改善提案の材料になる>

### 既存画面との違い（既存アプリの改善・機能追加のときだけ）

<既存アプリが独自の CSS で描いている部分と、デザインシステムで組み直した prototype との見た目の違い。
レビューする人が「実際の画面と違う」と戸惑わないように書く>
````

## 書くときの注意

- **PRD の段階では、新しい画面の話をしない。** 「一覧画面にフィルターを置く」は機能構成に書く。PRD に書くのは「目的のイベントをすぐ見つけたい」まで。ただし既存画面の改善なら、今の画面がどうなっていて何が困るかは「背景と課題」に書いてよい。
- **ストーリーは全部どこかの画面に対応させる。** 機能構成の「対応ストーリー」列に出てこないストーリーがあれば、画面が足りないか、範囲外に移すべきかのどちらか。
- **複数案を比較するなら、案ごとに「画面一覧」と「画面ごとの状態」を書く。** 画面名は「案A 一覧＋プレビュー」のように案の名前から始める。PRD とデータは共通にする。
- **状態は、利用者が実際に出会うものに絞る。** 状態の表の行がそのまま mockup のフレームになるので、多すぎると見るのが大変になり、少なすぎると空状態やエラーの検討が漏れる。目安は 1 画面に 1〜4 状態。
- **コンポーネントは DESIGN.md の意図に沿って選ぶ。** たとえば `Tooltip` に必須情報を入れない、`toast` だけでエラーを伝えない、primary ボタンは 1 画面に 1 つ。

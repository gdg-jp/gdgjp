# spec.md のテンプレート

`spec.md` は、PRD・機能構成・コンポーネント選定を 1 つにまとめたファイルです。
ビルドすると HTML の「仕様」タブに表示され、mockup をレビューする人は、何を満たすための画面なのかをこのタブで確かめます。
そのため、読み手は依頼者とは限らないと考えて書きます。

各見出しの役割は次のとおりです。

- **PRD:** 「誰の、何を、なぜ、どう解くか」。Overview、Goal / Non-goal、Proposed solutions、User stories、Open questions / Risks の 5 節で書く。
- **機能構成:** 「どんな画面と流れで」。PRD のユーザーストーリーをすべて画面に割り当てる。
- **コンポーネント選定:** 「どの部品で」。機能構成の各画面を `@gdgjp/design-system` の部品に落とす。

前の章が決まらないと後の章は書けません。
後の章で矛盾が見つかったら、前の章に戻って直します。

## 目次

1. テンプレート
2. PRD の原則（less is more、MECE、5W1H）
3. PRD の例
4. PRD を確認に出す前のセルフチェック
5. 機能構成とコンポーネント選定の注意

## 1. テンプレート

````markdown
# <プロダクト名・機能名>

## PRD

### Overview

<1〜2 文。誰の、どんな課題を、どう解くか>

| 5W1H | 内容 |
| --- | --- |
| Who | <使う人。役割だけでなく状況まで。例: 当日だけ手伝うボランティアの受付スタッフ> |
| What | <その人がすること> |
| When | <いつ、どんな場面で> |
| Where | <どこで、どの端末で> |
| Why | <今なにが困っているか。具体的な場面か数字で> |
| How | <どう解くかの一言。詳しくは Proposed solutions> |

### Goal / Non-goal

**Goal**

- G1: <達成したい結果。観察か計測ができる形で>

**Non-goal**

- <この PRD では扱わないこと。隣にあって含まれると誤解されやすいものを選び、理由を一言添える>

### Proposed solutions

- S1（G1）: <解決策。仕組みと振る舞いで書く。画面の配置は機能構成に書く>
- 守る制約: <既存の決まり（ADR、権限、公開範囲など）。なければこの行は消す>

### User stories

| ID | ストーリー | Goal | 優先度 |
| --- | --- | --- | --- |
| US-1 | <Who> として、<When / Where> に <What> したい。<Why> のため。 | G1 | Must |

### Open questions / Risks

| 種類 | 内容 | 今の扱い |
| --- | --- | --- |
| Question | <決まっていないこと> | <仮定（未確認）: 選んだ案> |
| Risk | <決めても残る不確かさ> | <この prototype での確かめ方、または対策> |

## 機能構成

### 画面一覧

| 画面 | 目的 | 主な操作 | 対応ストーリー |
| --- | --- | --- | --- |
| <イベント一覧> | <…> | <検索、作成、詳細へ> | US-1, US-2 |

### 画面遷移

```text
イベント一覧 ──[作成]──▶ 作成ダイアログ ──[保存]──▶ イベント一覧（トースト）
     │
     └──[行を選択]──▶ イベント詳細 ──[削除]──▶ 確認ダイアログ
```

### 画面ごとの状態

mockup に並べるフレームは、この表の行と 1 対 1 で対応します。
起こりうる状態だけを挙げてください（すべての画面に「エラー」が要るわけではありません）。

| 画面 | 状態 | どんなときに起きるか | frame id |
| --- | --- | --- | --- |
| イベント一覧 | 通常 | 予定が数件ある | `events` |
| イベント一覧 | 0 件 | 初めて使う | `events-empty` |
| イベント一覧 | 通常（モバイル） | スマートフォンで確認 | `events-mobile` |
| 作成ダイアログ | 入力エラー | 必須項目が空のまま保存 | `create-error` |

### データ

画面に出す項目だけを書きます（DB 設計ではありません）。

| もの | 項目 |
| --- | --- |
| イベント | 名前、開催日、開催形式（会場／オンライン／ハイブリッド）、公開状態、参加者数 |

## コンポーネント選定

| 画面・領域 | コンポーネント | 選んだ理由・使い方 |
| --- | --- | --- |
| 全体の枠 | `AppShell` | サイドバー付きの管理画面。モバイルでは Sheet に畳まれる |
| 一覧 | `Table` + `Badge` | 比較が要る構造化データ。公開状態は `Badge` の tone で表す |
| 0 件 | `EmptyState` | 作成ボタンを `action` に置く |
| 作成 | `Dialog` + `FormField` + `Input` | 項目が少なく、一覧の文脈を保ったまま作成できる |
| 結果通知 | `toast` | 成功だけに使う。エラーは `FormField` の `error` に出す |

### デザインシステムにないもの

<既存コンポーネントの組み合わせで代用したもの、代用できず自作したもの、見た目を上書きしたものと、その理由。
なければ「なし」と書く。デザインシステムへの改善提案の材料になる>

### 既存画面との違い（既存アプリの改善・機能追加のときだけ）

<既存アプリが独自の CSS で描いている部分と、デザインシステムで組み直した prototype との見た目の違い。
レビューする人が「実際の画面と違う」と戸惑わないように書く>
````

## 2. PRD の原則

PRD は、画面を決めるための最小の合意です。
次の 3 つを守ります。

### Less is more

PRD を読む人は、prototype を見る前の数分で「何のための画面か」を掴みたいだけです。
長い PRD は読まれず、本当に大事な 1 行が埋もれます。

- **残す基準は「この行が消えたら、画面の何が変わるか」。** 何も変わらない行は消す。
- **一般論と形容詞を書かない。** 「使いやすく」「シンプルに」「直感的に」は、どの PRD にも当てはまり、何も決めない。
- **量の目安:** Goal は 1〜3 個、Non-goal は 2〜5 個、Proposed solutions は Goal の数前後、User stories は 3〜7 個（Must は 3 個前後）、Open questions / Risks は 3〜5 個。超えたら、まとめるか、範囲を絞って Non-goal に送る。
- **表と箇条書きで書く。** 段落の文章は Overview の要約 1〜2 文だけにする。

### MECE

漏れがあると画面が足りなくなり、重なりがあると同じ画面を 2 回作ります。

- **Goal 同士が重ならず、合わせると Overview の Why を言い尽くす。** 言い尽くさないなら Goal が足りない。重なるなら 1 つにまとめる。
- **Goal と Non-goal が重ならない。** Non-goal には、隣にあって含まれると誤解されやすいもの（通知、権限管理、分析など）を挙げる。
- **すべての User story がどれかの Goal に対応し、すべての Goal に User story がある。** 同じ要求を言い換えた story を作らない。
- **Proposed solutions はすべてどれかの Goal に対応する。** Goal に効かない解決策は、Non-goal に送るか消す。
- **Question と Risk を混ぜない。** Question は「決めれば消えるもの」、Risk は「決めても残る不確かさ」。

### 5W1H

画面の形を決めるのは、主に Who・When・Where です。
片手で数秒で操作するのか、PC で腰を据えて操作するのかで、同じ機能でも画面がまったく変わります。

- **Overview の 5W1H 表は 6 行すべて埋める。** 分からない行は空欄にしない。もっともらしい仮定で埋め、同じ内容を Open questions に「仮定（未確認）」として載せる。
- **Who は役割名だけでなく、状況まで書く。** 「スタッフ」ではなく「当日だけ手伝うボランティアの受付スタッフ」。慣れているか、何人いるかが画面を変える。
- **Why は具体的な場面か数字で書く。** 「効率が悪い」ではなく「紙の名簿から名前を探すのに 1 人 30 秒かかる」。
- **User story でも、Who・When / Where・What・Why が読み取れるようにする。** 「〜できる」だけの story は、誰がいつ使うかが抜けている。

## 3. PRD の例

DevFest の当日受付を、スタッフのスマートフォンでできるようにする例です。
この長さで十分です。

```markdown
## PRD

### Overview

当日だけ手伝うボランティアが、来場者を QR か名前で見つけて、その場でチェックインできるようにする。

| 5W1H | 内容 |
| --- | --- |
| Who | 当日だけ手伝うボランティアの受付スタッフ（10 名程度、初めて使う人が多い） |
| What | 来場者を見つけてチェックインする。間違えたら取り消す |
| When | 開場からの 1 時間。列が途切れない |
| Where | 会場の入口。立ったまま、自分のスマートフォンを片手で持つ |
| Why | 紙の名簿から名前を探すのに 1 人 30 秒かかり、開場直後に列が伸びる |
| How | QR の読み取りを主にし、QR を出せない人は名前で探す |

### Goal / Non-goal

**Goal**

- G1: 1 人あたりの受付を 10 秒以内にする
- G2: 二重受付と受付間違いを、その場で気づいて直せるようにする

**Non-goal**

- 当日の参加登録（受付で新しく登録しない。connpass 側で行う）
- 受付データの分析（イベント後に別途行う）

### Proposed solutions

- S1（G1）: カメラで QR を読み取ると、確認なしで受付を完了する
- S2（G1）: QR を出せない人は、名前の一部・かな・受付番号で探して受付する
- S3（G2）: 受付済みの人を読み取ると警告し、直近の受付から取り消せる
- 守る制約: 参加者の個人情報は名前と所属だけを表示する

### User stories

| ID | ストーリー | Goal | 優先度 |
| --- | --- | --- | --- |
| US-1 | 受付スタッフとして、列が続いているあいだに QR を読むだけで受付したい。待たせないため。 | G1 | Must |
| US-2 | 受付スタッフとして、QR を出せない人でも名前の一部から見つけたい。列を止めないため。 | G1 | Must |
| US-3 | 受付スタッフとして、受付済みの人や間違えた受付にその場で気づいて直したい。人数を正しく保つため。 | G2 | Must |

### Open questions / Risks

| 種類 | 内容 | 今の扱い |
| --- | --- | --- |
| Question | 同姓同名の人をどう見分けるか | 仮定（未確認）: 所属と受付番号を並べて表示する |
| Question | 会場の電波が弱いときに受付を続けるか | 仮定（未確認）: 通信エラーを表示し、再試行させる |
| Risk | 逆光や画面の割れで QR が読めない | 名前で探す導線を QR の画面からすぐ出せるか、prototype で確かめる |
```

## 4. PRD を確認に出す前のセルフチェック

確認に出す前に、次をすべて満たしているかを見ます。
満たしていない項目は、直してから出します。

- [ ] Overview の 5W1H 表に空欄がない。仮定で埋めた行は Open questions にも載っている
- [ ] Goal は 1〜3 個で、観察か計測ができる。重なりがなく、合わせると Why を言い尽くす
- [ ] Non-goal に、含まれると誤解されやすい隣の機能が挙がっている
- [ ] すべての Proposed solution と User story に、対応する Goal がある。すべての Goal に User story がある
- [ ] User story から、Who・When / Where・What・Why が読み取れる
- [ ] Proposed solutions が画面の配置を語っていない（それは機能構成の仕事）
- [ ] 一般論、形容詞、同じことの言い換えが残っていない
- [ ] Open questions のうち、画面の形を変えるものが分かっている（それを AskUserQuestion で聞く）

## 5. 機能構成とコンポーネント選定の注意

- **既存画面の改善なら、今の画面がどうなっていて何が困るかを Overview の Why に書く。** PRD で画面の話をしてよいのは、この「今の画面」だけ。新しい画面の配置は機能構成に書く。
- **ストーリーは全部どこかの画面に対応させる。** 機能構成の「対応ストーリー」列に出てこないストーリーがあれば、画面が足りないか、Non-goal に移すべきかのどちらか。
- **複数案を比較するなら、案ごとに「画面一覧」と「画面ごとの状態」を書く。** 画面名は「案A 一覧＋プレビュー」のように案の名前から始める。PRD とデータは共通にする。
- **状態は、利用者が実際に出会うものに絞る。** 状態の表の行がそのまま mockup のフレームになるので、多すぎると見るのが大変になり、少なすぎると空状態やエラーの検討が漏れる。目安は 1 画面に 1〜4 状態。
- **コンポーネントは DESIGN.md の意図に沿って選ぶ。** たとえば `Tooltip` に必須情報を入れない、`toast` だけでエラーを伝えない、primary ボタンは 1 画面に 1 つ。
